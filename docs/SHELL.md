# Host shell

## Summary

This is the 0.3.1 Beta host contract. `export_shell!` exports one plugin as a C ABI named `op_shell_*`. A thin native adapter calls that ABI. The same symbols feed VST3, Audio Unit, and AAX. The Rust layouts in `openplugin-targets` are not loadable. The adapters are `native/vst3`, `native/au`, and `native/aax`. The adapters in this release are macOS.

`create` allocates the plugin and its scratch. `set_plain`, `set_normalized`, and `process` do not allocate. The audio thread applies the parameter plane inside `process`. `new` is not used from the audio thread.

The shell is mono or stereo, 32-bit float, and one plugin per binary. It hosts an editor only when the plugin exports the optional editor ABI (see Editor). AAX development IDs are a hash of the plugin id. `Plugin::aax_ids` replaces them with fixed four-character codes, which a release needs. The AAX controls packet is sized from the parameter count; the shell takes up to 4096 parameters.

## Export

```rust
openplugin_targets::export_clap!(EditorGain);
openplugin_targets::export_lv2!(EditorGain);
openplugin_targets::export_shell!(EditorGain);

// With an editor (macOS): the same three, plus `editor = make_editor`.
openplugin_targets::export_shell!(EditorGain, editor = make_editor);
```

The crate type includes `staticlib`. The native build links that archive. It does not sign or copy a plugin into a system folder.

## Allocation

| Call | Thread | Allocates |
|---|---|---|
| `op_shell_info`, `op_shell_param`, `op_shell_to_plain`, `op_shell_to_normalized` | message | no, after the first descriptor read |
| `op_shell_create` | message, while inactive | yes |
| `op_shell_destroy`, `op_shell_reset` | message, while inactive | `destroy` frees |
| `op_shell_set_plain`, `op_shell_set_normalized` | audio | no |
| `op_shell_process` | audio | no |
| `op_shell_save_state`, `op_shell_load_state` | message, any time | yes (the blob) |

`process` copies through scratch allocated in `create`, so an input pointer may be the output pointer. A null right pointer is mono. A block longer than the size passed to `create` fails. The adapters split a host block into that size. The prepared size is at most 65536 frames, and the AAX callback uses 2048.

Class IDs are 16 bytes from a 128-bit mix of the plugin id. VST3 prints them with `FUID::toString`, 32 hex digits. The processor id and the controller id differ. AAX manufacturer, product, mono, and stereo ids are four-byte values from that mix with bit `0x20` set in each byte so none is zero.

## Events, transport, buses and kind (ABI 2)

`op_shell_process` stays as it was and is now `op_shell_process_events` with no events, no sidechain and a stereo (or mono) bus. The new entry point carries everything a note-driven or multi-bus plugin needs, so each C++ shell can map its host's events onto it. Declarations are in `native/include/op_shell.h`; the Rust side is `crates/openplugin-ffi/src/block.rs` and `shell.rs`.

| Call | Thread | Allocates |
|---|---|---|
| `op_shell_abi_version`, `op_shell_kind`, `op_shell_note_ports`, `op_shell_layout_count`, `op_shell_layout` | message | yes (they build a plugin to ask it) |
| `op_shell_set_layout`, `op_shell_layout_selected` | message, before the first block | yes (new scratch) |
| `op_shell_set_offline` | any | no |
| `op_shell_param_format`, `op_shell_param_parse` (ABI 3) | message | yes (the text) |
| `op_shell_set_track_info` (ABI 4) | message | yes (the name) |
| `op_shell_process_events` | audio | no |
| `op_shell_midi_out`, `op_shell_midi_dropped` | audio thread, after the block | no |

### Versioning

`OP_SHELL_ABI` in the header is the ABI version the shell was written for; `op_shell_abi_version()` and `OpShellInfo.abi` are the version of the library. The rule:

- A version only adds: functions, enum values, struct fields at the end of a struct that carries `struct_size`. Nothing is removed, renamed or changed in meaning. Adding anything raises the number (1 was everything up to save/load state, 2 adds this section, 3 adds the parameter text calls below, 4 adds the host's track).
- A shell built against `OP_SHELL_ABI = N` works with any library of version N or higher, and must refuse a library below N (`op_shell_abi_version() < OP_SHELL_ABI`) instead of calling symbols that are missing. The shells that existed before ABI 2 compare `info.abi` for equality; they are built from the same header as the library, so that still holds. The Audio Unit shell (whose test stand-ins report the current ABI, and one reports an older one that must be refused) checks `op_shell_abi_version() >= OP_SHELL_ABI` and `info.abi >= OP_SHELL_ABI`; a library that fails the check leaves the unit without parameters, and `AudioUnitInitialize` returns `kAudioUnitErr_FailedInitialization`.
- A change that cannot be additive gets new symbol names (a new prefix), so a mismatch fails at load instead of misbehaving.

### Parameter text (ABI 3)

A host shows a parameter as text ("6.0 dB") and reads a value typed by the user. The plugin owns both texts: `ParamInfo::format` and `ParamInfo::parse`. Two calls hand them across, so a shell never invents its own.

- `size_t op_shell_param_format(uint32_t index, double plain, char* buf, size_t cap)` writes the text for the plain value as UTF-8 with a NUL. It returns the length of the whole text in bytes, not counting the NUL; the text was cut when that is `cap` or more. A cut falls on a UTF-8 boundary, and the NUL is written whenever `buf` is set and `cap > 0`. `buf` NULL writes nothing, so `buf` NULL with `cap` 0 asks for the length. An unknown `index` returns 0 and writes an empty string; a non-finite `plain` shows the default.
- `int op_shell_param_parse(uint32_t index, const char* text, double* out_plain)` reads NUL-terminated UTF-8 as `ParamInfo::parse` does (unit suffixes, choice labels, on/off, `-inf`; clamped to the range) and stores the plain value. It returns 1, or 0 with `*out_plain` untouched for a NULL pointer, an unknown index, text that is not UTF-8, text over 1024 bytes, or text that is not a value.

Both are for the message thread (they allocate), never the audio thread, and neither can panic across the ABI. The shell converts plain and normalized with `op_shell_to_plain` and `op_shell_to_normalized`. The formatted text is display only; the stored value is always the normalized one.

### The host's track (ABI 4)

A host tells a plugin which track it sits on (name, colour, and for CLAP whether it is a return, a bus or the master). One call hands it across:

- `uint32_t op_shell_set_track_info(void* instance, const char* name_utf8, uint32_t rgba, uint32_t flags)`. `name_utf8` is NUL-terminated UTF-8, or NULL for no name (invalid bytes are replaced; more than 255 characters are cut). `rgba` is `0xRRGGBBAA` and counts only with `OP_TRACK_HAS_COLOUR` (0x100) in `flags`. The low bits of `flags` are the kind, `OP_TRACK_RETURN` 1, `OP_TRACK_BUS` 2, `OP_TRACK_MASTER` 4; other bits are ignored. It reaches `Plugin::track_info_changed` on the calling thread.
- Message thread only; it allocates. It takes the plugin object between blocks, as a state call does: a block that starts meanwhile is passed through dry, and the call waits at most 2 seconds for a block already running. Returns 1 when delivered; 0 for a NULL instance or when it gave up. Safe to call while the audio thread is in `op_shell_process`.
- Call it again whenever the host says something changed, and for each new engine (the engine does not keep it across `op_shell_destroy`). The VST3 shell does both. The editor hears the same through `op_editor_set_track_info` ([EDITOR.md](EDITOR.md)).

The Audio Unit and AAX shells do not call it yet. `OP_SHELL_ABI` is 4; the Audio Unit proof's stand-in plugins were moved with it (the ones standing for the current library report 4, the newer one 5, the older one still 2).

### Channel order

ABI channel order is canonical; shells reorder. Every bus the ABI carries (main in, main out, sidechain) lists its channels in the SDK's order: the CLAP surround order of `openplugin_core::layout` (`SpeakerLayout::surround_map`), ambisonic buses in ACN. The ABI never exposes a host's order (VST3 speaker arrangements, Audio Unit layout tags, Pro Tools film order). A shell reorders at its own edge, between the host's buffers and the pointer arrays it hands to `op_shell_process_events`.

`op_shell_layout(index, &layout)` describes layout `index` (no instance needed). `OpLayout.input`, `.output` and `.sidechain` are `OpBus` values with a `kind` (`OP_BUS_ABSENT`, `MONO`, `STEREO`, `SURROUND`, `AMBISONIC`, `DISCRETE`, the `SpeakerLayout` kinds), a `channels` count, and `roles[i]`, the SDK role id of channel `i` (the CLAP surround ids 0 to 17, then 18 to 21 for top side and wide channels) (FL 0, FR 1, FC 2, LFE 3, BL 4, BR 5, and so on). Stereo is FL, FR. `roles[i]` is `OP_ROLE_NONE` (0xFF) for mono, ambisonic and discrete buses and past channel 16. A shell builds its reorder table from these roles and does not repeat `layout.rs`. `name` is the layout's label. A missing sidechain is `OP_BUS_ABSENT` with 0 channels.

#### Canonical order of every layout

Role ids: 0 FL, 1 FR, 2 FC, 3 LFE, 4 BL, 5 BR, 6 FLC, 7 FRC, 8 BC, 9 SL, 10 SR, 11 TC, 12 TFL, 13 TFC, 14 TFR, 15 TBL, 16 TBC, 17 TBR (the CLAP `CLAP_SURROUND_*` ids), then the SDK-only ids 18 TSL, 19 TSR (top side, the overhead pair of the x.y.2 beds; Dolby "top middle" Ltm/Rtm), 20 FLW, 21 FRW (front wides). CLAP has no ids for 18 to 21, so a layout that uses them (5.1.2, 7.1.2, 9.1.6) cannot be expressed through the CLAP surround extension: `SpeakerLayout::clap_expressible` is false, `surround_mask` and `clap_map` return `None`, and the CLAP entry must not offer them.

| Stereo | 2 | FL FR |
| LCR | 3 | FL FR FC |
| Quad | 4 | FL FR BL BR |
| 5.0 | 5 | FL FR FC BL BR |
| 5.1 | 6 | FL FR FC LFE BL BR |
| 6.1 | 7 | FL FR FC LFE BL BR BC |
| 7.1 | 8 | FL FR FC LFE SL SR BL BR |

The order is the SDK's own, not a host's: bed (L R C LFE), then the sides and backs, then the wides, then the heights from front to back, each pair left before right. It matches the Dolby Atmos home bed channel order (L R C LFE Lss Rss Lrs Rrs, wides, then front, top and rear heights) as the author recalls it; no standard document was available to check against, so treat the 9.1.6 and top side placements as the SDK's choice. ITU-R BS.2051 names the same speakers with different labels (for example U+030 for a front height) and a different order. 9.1.6 fills `OpBus::roles[16]` exactly; no layout exceeds 16 channels.

Role helpers on `SpeakerLayout` (all allocation-free; `index_of`, `role_at`, `is_lfe`, `roles` are `const`): `index_of(role)`, `role_at(i)`, `roles()`, `is_lfe(i)`, `non_lfe()` (indices), `pairs()` ((left, right) indices) and `unpaired()` (centre, back and top centre, LFE; every channel of a bus with no roles). Plugin code looks channels up by role and never hard-codes an index.

Every shell offers the beds and reorders them at its edge:

|---|---|---|---|---|---|

Every other cell is run by the role proof (Proof, "Channel order in every format"), which checks that every role arrives at its canonical index and returns to the host's channel for that speaker.

### Layout selection

`op_shell_layout_count()` is how many layouts the plugin offers; index 0 is its default. `op_shell_set_layout(instance, index)` selects one before the first block: it calls `Plugin::set_layout` and `prepare_layout`, and resizes the main and sidechain scratch to the layout's widths (main width is the larger of input and output, at least 1). It allocates and waits for a running block (at most two seconds), so it belongs to the activation step on the main thread. It returns 0, changing nothing, for a bad index, a layout the plugin refuses, or a timeout. `op_shell_create` still takes a channel count of 1 or 2; a shell that wants more selects a layout afterwards. `op_shell_layout_selected` reads the index back.

### The block

```c
OpProcess args = { sizeof args, frames, inputs, in_ch, out_ch, outputs,
                   sidechain, side_ch, event_count, events, &transport };
op_shell_process_events(instance, &args);
OpMidiEvent out[64];
uint32_t n = op_shell_midi_out(instance, out, 64);
```

- Audio is planar pointer arrays. `inputs` may be NULL with `input_channels` 0 (an instrument gets silence). One input channel feeds every channel of a wider engine bus. A NULL channel pointer reads as silence on an input and is skipped on an output. Inputs may alias outputs. Non-finite input samples read as 0.
- `struct_size` is `sizeof(OpProcess)` as the shell compiled it. A smaller value is refused, so fields can be appended later.
- Events (`OpEvent`): note on, note off (channel, note, velocity), raw 3-byte MIDI, and a parameter change as a plain or normalized value, each at a sample `offset` below `frames`. The list may be in any order; it is stably sorted. Delivery follows the CLAP bridge: the block is cut at each distinct offset, the events at that offset are applied (notes and MIDI reach the plugin at offset 0 of the next piece, parameters reach the plane), then the next piece is processed, so a parameter change is sample-accurate. Raw MIDI `0x9n` and `0x8n` reach `note_on_channel` / `note_off`, anything else `Plugin::midi`.
- Transport (`OpTransport`): `flags` carry playing and recording and say which fields the host knows (`OP_TRANSPORT_HAS_TEMPO`, `HAS_SIGNATURE`, `HAS_BEATS`, `HAS_SECONDS`); unknown fields take the `Transport` defaults. NULL keeps the previous transport and does not call `Plugin::set_transport`.
- Sidechain: `sidechain` and `sidechain_channels` (or NULL and 0). It reaches `Plugin::process_buses`; a plugin whose layouts have none ignores it. Channels the host did not send read as silence.
- MIDI output: after the block, `op_shell_midi_out(instance, out, capacity)` copies up to `capacity` `OpMidiEvent` (offset in the block, three bytes) into the caller's buffer and returns the count; call again for more. The engine keeps `OP_MAX_MIDI_OUT` (1024) events per block; extra events are dropped and counted by `op_shell_midi_dropped`. The next block clears what was not read. No allocation.
- Offline: `op_shell_set_offline(instance, 1)` reaches `Plugin::set_offline` at the start of the next block, with the same momentary-parameter release as CLAP.
- Kind: `op_shell_kind()` is `OP_KIND_INSTRUMENT` when `PluginInfo::is_instrument` is set or the category is `Instrument`; `OP_KIND_NOTE_EFFECT` when the plugin is not an instrument, writes notes (`note_ports().output`) and none of its layouts has an audio output; otherwise `OP_KIND_EFFECT`. `op_shell_note_ports()` returns `OP_NOTE_PORT_INPUT` and `OP_NOTE_PORT_OUTPUT` bits. No new `PluginInfo` field was needed.

### Refusals

`op_shell_process_events` returns 0 and touches no audio, no plugin and no parameter for: a NULL instance or `args`, a `struct_size` below the current struct, a NULL array with a non-zero count, more than 64 channels in any bus, more than `OP_MAX_EVENTS` (1024) events, or `frames` above the size given to `op_shell_create`. An individual bad event is skipped and the block still runs: an offset at or past `frames`, an unknown kind, a channel above 15, a note or velocity above 127, a raw message that is not a status byte plus two data bytes, a non-finite parameter value. A parameter index past the end is ignored by the plane. A block that starts during a state call is passed through dry (events lost) and returns 1, as for `op_shell_process`.

Tests: `crates/openplugin-ffi/tests/shell_events.rs` (notes, sorted and split delivery, MIDI out in pages, parameter changes at offsets, transport, sidechain, layouts and roles, selection, offline, kind, the old entry point, hostile input) and the events section of `shell_no_alloc.rs` (zero allocations and frees in the whole events path, refusals included).

### VST3 on ABI 2

`native/vst3/OpenPluginVST3.cpp` is a thin map from VST3 onto the calls above. The version rule is the one in Versioning: the shell calls `op_shell_abi_version()` and `op_shell_info` and refuses a library below `OP_SHELL_ABI` (it accepts a newer one). The controller's `ShellParameter` shows and reads values through the parameter text calls: `toString` is `op_shell_param_format` of the plain value, `fromString` is `op_shell_param_parse` converted to normalized (a text the plugin refuses is refused to the host). Text crosses as UTF-8 in the ABI and UTF-16 in VST3, with surrogate pairs. The bypass parameter reads "Off" and "On" and accepts on, off, 1, 0, yes, no, true and false; the hidden MIDI controller parameters keep the SDK's default text.

- **Processing.** `process` calls `op_shell_process_events`. Every point of every `IParameterChanges` queue is an `OP_EVENT_PARAM_NORMALIZED` event at its sample offset, so parameter changes stay sample-accurate; the engine cuts the block. The host bypass switch (`kIsBypass`) is not an engine parameter: its points cut the block in the shell, and the 10 ms crossfade to the latency-delayed input is unchanged. A block longer than the size given at `setupProcessing`, or with more than `OP_MAX_EVENTS` events, goes to the engine in consecutive chunks. Queues with more points than fit (4096, or the parameter count) are thinned as before, keeping each parameter's last value.
- **Notes in.** A plugin with `OP_NOTE_PORT_INPUT` gets one event input bus (16 channels). `kNoteOnEvent` and `kNoteOffEvent` become note events (velocity is the float scaled to 1..127; a note-on with velocity 0 is a note-off), `kPolyPressureEvent` becomes raw MIDI `0xAn`. Tuning and note expression are not carried yet (per-note expression is a later task).
- **MIDI controllers in.** The VST3 way for CCs, channel pressure and pitch bend is `IMidiMapping`, not events: the controller implements it and maps `(channel, controller number)` to a hidden parameter (`kIsHidden`); the host sends that parameter's changes through `IParameterChanges`, with sample offsets. A plugin with a note input has 16 x 130 such parameters (controllers 0..127, `kAfterTouch` 128, `kPitchBend` 129), ids from `0x4D494400`, clear of the plugin's `0..n-1` and the bypass id. The processor turns each point into raw MIDI (`0xBn`, `0xDn`, `0xEn` with 14 bits). `kLegacyMIDICCOutEvent` on the event input is accepted as well, for hosts that still send it (CC, pressure, pitch bend, program change, polyphonic pressure).
- **MIDI out.** A plugin with `OP_NOTE_PORT_OUTPUT` gets one event output bus. After each chunk the shell reads `op_shell_midi_out` and adds events at the chunk's offset: `0x9n`/`0x8n` as `kNoteOnEvent`/`kNoteOffEvent` (note id -1), `0xAn` as `kPolyPressureEvent`, and controllers, program change, channel pressure and pitch bend as `kLegacyMIDICCOutEvent`, VST3's form of raw MIDI. System messages are dropped.
- **Transport.** `ProcessContext` becomes `OpTransport` each block (a host that sends none keeps the last, as the ABI says). Playing and recording map directly. Tempo, signature and quarter notes are passed only when the host marks them valid. `sample_pos` is `projectTimeSamples`; `seconds` is that over the sample rate. VST3 has no bar number: `bar_start` is `barPositionMusic` when valid, else the start of the bar holding the position under the current signature, and `bar_number` is `bar_start` over the bar length (zero-based, right while the signature is constant).
- **Buses and layouts.** Buses follow the plugin's layouts (`op_shell_layout*`): a main input if any layout has input, a main output if any has output, an event bus per note port, and an aux input ("Sidechain", `kAux`, not `kDefaultActive`) if any layout has a sidechain. An instrument has no audio input bus; a note effect has no audio bus. `setBusArrangements` accepts a set of arrangements that equals the buses of one layout and selects it (`op_shell_set_layout` at the next `setActive`); anything else returns false and changes nothing, so the host reads the current arrangement back with `getBusArrangement`. A host that names no aux bus leaves the sidechain to the plugin. A plugin that declares only the default stereo layout still accepts mono in and out, as shells before ABI 2 did (the engine gets a one-channel bus); a plugin whose layouts VST3 cannot name falls back to mono and stereo.
- **Channel order.** VST3 channels sit in ascending speaker-bit order. Bits 0..17 (L R C Lfe Ls Rs Lc Rc Cs Sl Sr Tc Tfl Tfc Tfr Trl Trc Trr) are numbered like the CLAP surround ids, so a speaker's role is its bit number; the shell builds a table from the layout's `roles[]` and hands the engine pointer arrays in the SDK's order. 7.1 differs between the two (VST3: L R C Lfe Ls Rs Sl Sr; SDK: FL FR FC LFE SL SR BL BR) and is reordered; 5.1 and 7.1.4 match. The SDK-only roles have their own VST3 speakers: TSL and TSR are `kSpeakerTsl` and `kSpeakerTsr` (bits 24, 25), FLW and FRW are `kSpeakerLw` and `kSpeakerRw` (bits 59, 60). So the beds are the SDK's named arrangements: 5.1.2 is `k51_2_TS` (L R C Lfe Ls Rs Tsl Tsr; `k51_2` has front heights Tfl Tfr instead and is refused), 5.1.4 is `k51_4`, 7.1.2 is `k71_2` (L R C Lfe Ls Rs Sl Sr Tsl Tsr) and 9.1.6 is Dolby's `k91_6_W` (with wides; the ITU `k91_6` has Lc Rc and is refused). In host order the wides come last (bits 59, 60), after the top side pair, so 9.1.6 is reordered. `static_assert`s in the shell check every bed's arrangement against the SDK constant. Mono is `kSpeakerM`; ambisonic buses are the ACN speakers up to 4th order. Discrete buses, ambisonics beyond 4th order and layouts with `Lfe2` cannot be named in VST3 and are not offered. Only the `k71Music` 7.1 (Ls Rs Sl Sr) matches the SDK's 7.1; `k71Cine` (Lc Rc) is refused. Bypass pairs host input channel `h` with host output channel `h`.
- **Offline.** `ProcessData::processMode == kOffline` calls `op_shell_set_offline(1)` when it changes (`kRealtime` and `kPrefetch` clear it).
- **Category.** From `op_shell_kind()`: an instrument is `Instrument|Synth` (or the plugin's own `Instrument|...`); an effect keeps the library's category (`Fx|EQ`, ...); a note effect is `Fx`, with event buses and no audio.
- **Parameter text.** `ShellParameter::toString` and `fromString` call `op_shell_param_format` and `op_shell_param_parse` (ABI 3), so the host shows the plugin's own text and typed values go through `ParamInfo::parse`.

### AAX (ABI 2)

The AAX shell (`native/aax`) calls `op_shell_process_events` for every block and takes every part of ABI 2. Citations are to AAX SDK 2.8.1 (`Interfaces/` and `Documentation/Doxygen/dox`). The proofs are `aax_events_proof`, `aax_describe_proof` and the parameter text proofs; none of this ran inside Pro Tools.

- **Version.** The shell refuses a library whose `op_shell_abi_version()` is below `OP_SHELL_ABI` and accepts a newer one. Describe, the data model's `EffectInit` and `ProcessState::prepare` all check it.
- **Parameters.** The controls packet carries plain values. A packet has no sample offset (`AddDataInPort` ports are delivered when the callback starts), so a value that differs from the engine's own (`op_shell_get_plain`) becomes an `OP_EVENT_PARAM_PLAIN` at offset 0, the start of the AAX buffer. Comparing with the engine rather than with the last packet repairs a value lost to a block that ran during a state call. The event list holds 1024 events: MIDI takes its room first and parameter changes beyond the rest (only on a first block of a plugin with more than about a thousand parameters) are set with `op_shell_set_plain`. Non-finite values still silence the block.
- **MIDI.** A plugin whose `op_shell_note_ports()` has `OP_NOTE_PORT_INPUT` gets a local MIDI input node (`AAX_eMIDINodeType_LocalInput`, all 16 channels); with `OP_NOTE_PORT_OUTPUT` a local output node. Packets (`AAX_CMidiPacket`) carry `mTimestamp`, a sample offset from the start of the buffer, and become note on, note off (a note on with velocity 0 is a note off) or raw MIDI events at that offset. A timestamp past the buffer is clamped to the last sample so a note off is never lost. Packets the ABI does not carry are dropped: SysEx (`0xF0`, `0xF7`), more than three bytes, a data byte over 127, an empty packet. MIDI from `op_shell_midi_out` is posted with `AAX_IMIDINode::PostMIDIPacket` at its offset, 64 events at a time. Pro Tools passes on only note on and off, pitch bend, polyphonic key pressure, bank select (controller 0), program change and channel pressure from a plug-in (`AAX_IMIDINode.h`); other controllers the plugin writes are dropped by the host, not by the shell. A plugin with a MIDI input is declared not multi-mono (`AAX_eProperty_Constraint_MultiMonoSupport` false), as Avid's synth example does.
- **Transport.** Every component has a transport node (`AAX_eMIDINodeType_Transport`) and the effect says `AAX_eProperty_UsesTransport`. Once per callback the shell asks the node's `AAX_ITransport` for tempo, meter, playing, the tick position and, during playback, the native sample location, and fills an `OpTransport` on the stack. There is no lock and no allocation, and no state shared with the data model. The node's interface is not versioned (`AAX_IMIDINode::GetTransport`), so only five version 1 methods are called (`GetCurrentTempo`, `GetCurrentMeter`, `IsTransportPlaying`, `GetCurrentTickPosition`, `GetCurrentNativeSampleLocation`); each failure leaves its flag clear. Ticks are 1/960000 of a quarter note (`AAX_ITransport.h`), so `quarter_notes` is ticks / 960000. The sample location is documented valid during playback only, so a stopped transport has no sample position or seconds. `bar_number` and `bar_start` are computed from the current meter as if it held for the whole timeline (AAX gives the meter at the current position only; bar 0 starts at quarter 0). AAX gives no record state, so `OP_TRANSPORT_RECORDING` is never set. A callback longer than the engine block (2048 frames) is processed in pieces; each piece's transport advances by its offset at the current tempo. The AAX bug list says tick and sample positions can run early behind inserts that add latency; the shell passes what the host gives.
- **Sidechain.** A layout with a sidechain bus adds `AddSideChainIn` (and `AAX_eProperty_SupportsSideChainInput`) to that stem's component. AAX gives the side chain as one extra input channel after the main inputs, at the index in the side-chain field, 0 when nothing is connected (`AAX_AdditionalFeatures_AOSandSidechain.doxygen`). Connected, it is the engine's sidechain, one channel; not connected, the engine gets none and reads silence. Pro Tools supports a mono side chain only (`AAX_eProperty_SideChainStemFormat` in `AAX_Properties.h`), so a wider sidechain bus gets channel 0 and its other channels read as silence. If two layouts have the same stems and only one has a sidechain, the one with it describes the component.
- **Stems and channel order.** One component is described for each stem pair found in the layouts (`buildConfigs`), with its own plug-in ID. The IDs of mono and stereo are the ABI's `plugin_id_mono` and `plugin_id_stereo`; any other is a hash of the stereo ID and the two stem formats with bit `0x20` set in every byte. A layout whose bus has no AAX stem is not offered. A plugin that declares stereo but not mono is still offered as mono through the ABI 1 one-channel engine, as it was before 0.6; an instrument or note effect is not. The stems and the order of their channels are the comments on `AAX_EStemFormat` in `AAX_Enums.h`, Pro Tools' film order. The shell reorders by role, with pointers only (no sample is copied), in both directions:

| AAX stem | Channels in Pro Tools order | SDK roles |
|---|---|---|
| Mono, Stereo | M; L R | none; FL FR |
| LCR | L C R | FL FC FR |
| Quad | L R Ls Rs | FL FR BL BR |
| 5.0, 5.1 | L C R Ls Rs (LFE) | FL FC FR BL BR (LFE) |
| 6.1 | L C R Ls Cs Rs LFE | FL FC FR BL BC BR LFE |
| 7.1 (`AAX_eStemFormat_7_1_DTS`) | L C R Lss Rss Lsr Rsr LFE | FL FC FR SL SR BL BR LFE |

  The LFE is last on 5.1 and eighth on 7.1 and 7.1.4, not fourth as in the SDK's order, and the centre is second, not third. A bus matches a stem by kind, channel count and set of roles, so the order the plugin lists them in does not matter. The 7.1 offered is the DTS-style stem, not `AAX_eStemFormat_7_1_SDDS` (L Lc C Rc R Ls Rs LFE), whose Lc and Rc have no counterpart among the 7.1 roles. The Atmos beds are stems too: the top-middle and top-side pairs (Ltm Rtm, Lts Rts) both map to the SDK's top side roles `TSL` 18 and `TSR` 19 (no stem has both), and the wides Lw Rw to `FLW` 20 and `FRW` 21; the orders are the `AAX_EStemFormat` comments. A bus whose roles no stem can place (for example 5.1 with wides) is not offered, and nothing in the shell is indexed by role, so ids above 17 are safe. Not mapped: the SDDS stems (Lc, Rc), LCRS and 6.0 (not needed by an SDK layout). Buses wider than 16 channels, discrete buses and ambisonics above third order are not offered.
- **Parameter text.** Every parameter's display delegate (`AAX_IDisplayDelegate<float>`, the shell's `ShellDisplay`) calls `op_shell_param_format` in `ValueToString` and `op_shell_param_parse` in `StringToValue`, so Pro Tools shows `6.0 dB`, choice labels and `Off`/`On`, and a typed `6 dB` is read by the plugin. The real value of an `AAX_CParameter<float>` is the plain value, so the SDK's linear or log taper is unchanged. The master bypass keeps its own `Off`/`On` delegate. Main thread only: the calls allocate, and the host reaches them through `GetParameterStringFromValue` and `GetParameterValueFromString`, never from the algorithm callback. The host's character limit (`maxNumChars`) is honoured by `ValueToString(value, max, ...)`, which the SDK's `GetParameterStringFromValue` passes; `AAX_CParameter::GetValueString(max, ...)` ignores the limit, so the shell overrides `GetParameterValueString` to honour it too. The ABI has no short form of a parameter's text, so a short request is made from the full text and the first form that fits wins: the whole text, the text without spaces (`6.0dB`), the number alone when the text starts with one (`6.0`), then the text cut on a UTF-8 boundary (trailing spaces dropped). The limit is counted in bytes, so the result is never longer than asked however the host counts characters; a negative limit fails. Proofs: `aax_text_proof` (example: Gain +6 dB reads `6.0 dB`, `6 dB` reads back as +6 dB, Warm reads `Off`/`On`, short limits) and `aax_text_stub_proof` (stand-in ABI: choice labels, toggle, multi-byte text cut safely). Not run inside Pro Tools.
- **Kind.** `OP_KIND_INSTRUMENT` is `AAX_ePlugInCategory_SWGenerators`; its stems are the output stem on both sides (AAX wants an input stem; the shell ignores the audio in it and gives the engine none). `OP_KIND_NOTE_EFFECT` is `AAX_EPlugInCategory_MIDIEffect`; its audio passes through unchanged (Avid's MIDI effect examples do the same), mono and stereo, and the engine gets no audio. An audio effect keeps the EQ and Dynamics words of the plugin's category string, and is otherwise `AAX_EPlugInCategory_Effect`.
- **Offline.** AAX has AudioSuite as a separate plug-in type (`AAX_IHostProcessor`, offline-only properties); this shell describes real-time plug-ins only and does not describe AudioSuite. For a real-time insert the SDK has no offline field in the process context. The one signal is the pair of notifications `AAX_eNotificationEvent_EnteringOfflineMode` and `ExitingOfflineMode` ("offline bounce", Pro Tools 11 and later, `AAX_Enums.h`), which the data model turns into `op_shell_set_offline`. `aax_describe_proof` delivers them to the shell's data model and sees the flag change in the plugin. Whether Pro Tools sends them to the data model or only to the GUI (the header says some notifications go to one only) cannot be checked without Pro Tools, so a plugin that needs offline rendering in AAX should treat this as best effort. A host that sends nothing leaves the flag false; nothing is guessed from the buffer size or the clock.
- **Bypass.** The engine keeps running while bypassed, so a note or MIDI the plugin produces still goes out; audio is the delayed input as before.

## Plugin state

`op_shell_save_state` and `op_shell_load_state` carry the whole plugin state across the ABI: the parameter plane and the plugin's own chunk (`Plugin::save_state` / `load_state`) in one opaque blob, the OPCH session of `openplugin_core::encode_session`. A shell stores the blob as its host state and hands it back later. The VST3 shell (see VST3 state), the Audio Unit shell (see Audio Unit state) and the AAX shell (its state chunk, payload version 2) call them.

```c
uint32_t op_shell_save_state(void* instance, uint8_t* out, uint32_t capacity, uint32_t* needed);
uint32_t op_shell_load_state(void* instance, const uint8_t* data, uint32_t length);
// op_shell_save_state results: OP_STATE_FAILED 0, OP_STATE_OK 1, OP_STATE_TOO_SMALL 2
```

- Save: `out` NULL with `capacity` 0 is a size query. The call returns `OP_STATE_TOO_SMALL` and writes the length to `*needed` (which may be NULL). Allocate that many bytes and call again. `OP_STATE_OK` means the blob is written and `*needed` is its length. If the state grew in between, the second call returns `OP_STATE_TOO_SMALL` again with the new size, so loop until OK. A short buffer is never written. `OP_STATE_FAILED` is a null instance, a null `out` with capacity above 0, a plugin that panics, a state over 4 GiB, or a timeout (below).
- Load: returns 1 or 0. It is all or nothing. The envelope (magic, version, every length, the parameter count, finite values) is checked before the plugin is touched. A corrupt, truncated, extended or foreign blob, an empty one, a null pointer, or a chunk the plugin's `load_state` refuses returns 0 and leaves the parameters and the plugin as they were. A plugin whose `load_state` returns false must have changed nothing itself: the SDK cannot undo a plugin's partial write. A bare OPST parameter plane (what the shells wrote before) still loads, and leaves the plugin's chunk alone.
- ABI: this was added without changing anything existing (`OP_SHELL_ABI` was 1 then; it is 2 since the events block, see Versioning), and a shell that does not call the new symbols builds as before. Both are declared in `op_shell.h` without a guard; a plugin built with `export_shell!` always exports them.

### Threading

A host calls get and set state on the main thread while its audio thread may be inside `op_shell_process`. `Plugin::save_state` takes `&mut self`, so a state call needs the plugin object to itself. One atomic gate decides who has it, and the audio thread never waits:

- `op_shell_process` (and `op_shell_reset`) enter the gate with one compare-exchange, no lock and no allocation. If a state call holds or has asked for the gate, the block is skipped: the input is copied to the output (a dry block, a null right input follows the left), the plugin is not entered, and `process` still returns 1. A `reset` that cannot enter is remembered and runs at the start of the next block, so the Audio Unit's render-thread reset is safe beside a state call.
- A state call takes a mutex against other state calls, sets a request bit, and waits for a block already in flight to end. New blocks see the request bit and skip, so a busy audio thread cannot starve it. The wait is bounded at 2 seconds (`openplugin_ffi::STATE_WAIT`); after that the call fails and changes nothing. The wait happens on the calling (main) thread only.
- Request bit and in-flight bit are one atomic word: for any block and any state call, either the block sees the request and skips, or the call sees the block and waits. No block runs against a half-restored plugin; a load applies the chunk and the plane before it releases the gate, so the next block sees both.

### Parameter-only plugins

A plugin whose whole state is its parameter values returns `true` from `Plugin::state_is_parameters_only` (the SDK's examples do). Its saves and loads never take the gate: a save reads the parameter plane, which the audio thread only reads, and a load validates the whole session and stores the values in the plane, which the engine pulls at the start of its next block. No block is ever skipped. A block that starts while a load is storing values can see some new values and some old ones for that one block. A chunk found in a saved session is ignored, because the plugin declared it has none. The default is `false`: the SDK cannot tell from outside whether a plugin overrides `save_state`, and a wrong guess would drop a chunk. The answer is read once, when the instance is built. CLAP follows the same rule. Tests: `crates/openplugin-ffi/tests/state_param_only.rs` (audio over 4000 blocks is bit-identical to an untouched run while another thread saves and loads; round trips and hostile sessions for both kinds of plugin) and `state_param_only_no_alloc.rs`.

Cost: a block is lost (replaced by dry audio) only when it starts during a call, for as long as `save_state` or `load_state` takes. A host that needs gap-free audio calls these while the transport is stopped or the unit is inactive, when no block is running. Never call them from the audio thread: they allocate and may wait. Before a save the gate holder applies the parameter plane to the plugin, so the chunk matches the values saved beside it; after a load every parameter is pushed to the plugin again on the next block.

The tests are `crates/openplugin-ffi/tests/shell_state.rs` (round trip, size protocol, hostile blobs), `shell_state_threads.rs` (a block during a held save is dry, a save waits for a block in flight, the bounded timeout, and two threads alternating two states against a rendering thread: no torn block, no torn blob) and `shell_state_no_alloc.rs` (zero allocations and frees on the audio thread while a save or a load holds the gate and during repeated calls).

## Editor

A plugin with an editor exports `op_editor_*` (`native/include/op_editor.h`) next to `op_shell_*`, and the shells are configured with `-DOP_EDITOR=ON`. Without that option the shells build as before and a host shows its generic controls. `export_shell!(P, editor = make_editor)` writes these symbols in Rust over `openplugin_dri::cocoa::EditorView`, for any `openplugin_core::Editor` (see [EDITOR.md](EDITOR.md)). The Rust view draws with AppKit, CoreGraphics and libobjc. A static library does not carry its framework links, so `native/CMakeLists.txt` names those frameworks for every target that links the archive, proofs included. That is necessary even with `-DOP_EDITOR=OFF` when the plugin still exports the editor ABI, as `examples/editor` does: the option only decides whether the shells host the view.

| Call | Does |
|---|---|
| `op_editor_size` | size in points the editor opens at |
| `op_editor_size_range`, `op_editor_get_size`, `op_editor_adjust_size`, `op_editor_resize`, `op_editor_set_request_resize` | the `OP_EDITOR_RESIZE` block, which `-DOP_EDITOR=ON` defines for the shells: the sizes the editor takes, its current size, the nearest accepted size, a new size, and the callback an editor uses to ask the host for one |
| `op_editor_create(host)` | makes the editor, bound to no engine; `host` carries the three gesture callbacks |
| `op_editor_view`, `op_editor_attach(parent)` | the `NSView`, and adding it to a host parent view |
| `op_editor_bind(instance)` | shows the engine from `op_shell_create`; null or a destroyed instance shows host values only |
| `op_editor_set_plain(index, plain)` | a parameter value from the host |
| `op_editor_destroy` | removes the view and frees the editor |

Every call is on the main thread. A gesture goes editor to shell to host through `begin_edit`, `perform_edit` and `end_edit`, with plain values, and the host returns the value to the engine as an ordinary parameter change. The editor never writes to the engine.

The shells recreate the engine when the host reconfigures them, so each one binds the open editor again:

- VST3: the processor sends the controller a message (`openplugin.engine`) when it creates or destroys its engine. This needs the processor and controller in one process, connected by the host. A host that does not connect them gets a working editor without meters.
- Audio Unit: the Cocoa view polls its Audio Unit 20 times a second for the engine and the parameter values. On the same timer it logs any failed initialize or render status, because a host renders silence for a failed block and reports nothing. The view class names carry the product name and version, because Objective-C class names are global in the host process.
- AAX: the view reads the engine through `GetCustomData` and sets values through `AAX_IParameter` (`Touch`, `SetValueWithFloat`, `Release`).

`op_editor_bind` must tolerate a pointer that is no longer a live instance. `openplugin_ffi::shell` keeps a table of live instances. `op_editor_bind` hands the editor the instance's `Plugin::editor_state` only when the pointer is in that table.

## Audio Unit reset

A host may call `AudioUnitReset` from its main thread while its render thread is inside the engine, and `op_shell_reset` is exclusive with `process`. The Audio Unit shell therefore only marks the reset, and the render thread performs it at the start of its next block.

## Audio Unit state

The Audio Unit shell overrides `SaveState` and `RestoreState`, the two calls behind `kAudioUnitProperty_ClassInfo`. The dictionary keeps every key `AUEffectBase` writes (version, type, subtype, manufacturer, `data`, name), so hosts and presets stay standard, and gains one more: `OpenPluginState`, CFData holding the blob of `op_shell_save_state`.

- Save: the unit's parameter values are stored into the engine first (the engine otherwise sees them only at the next block), then the blob is fetched with the size protocol: query with `(NULL, 0)`, allocate `*needed`, call again, repeat while the result is `OP_STATE_TOO_SMALL` (up to 8 times). Without an engine (before Initialize) the state held since the last restore is written, if any. If the plugin cannot save, the key is left out and the parameters still save.
- Restore, key present: the blob goes through `op_shell_load_state` first. A refused blob (corrupt, truncated, foreign, a chunk the plugin refuses, or a value of the wrong type under the key) refuses the whole dictionary with `kAudioUnitErr_InvalidPropertyValue` and nothing changes: not the plugin chunk and not the parameters the base keys carry. An accepted blob is followed by the base restore, and then the unit's parameters are read back from the engine, so where the two disagree the blob wins. If the base restore fails after the blob loaded, the earlier state is loaded back.
- Restore, key absent (a preset from before this key): the base restore only, as before; the plugin's chunk is left as it is.
- Before Initialize there is no engine. The blob is then checked on a scratch engine (`op_shell_create` at the unit's sample rate, two channels), refused or accepted by the same rule, kept, and loaded into the real engine at Initialize. Uninitialize keeps the engine's state the same way for the next Initialize. A parameter set between the restore and Initialize is kept.
- Threads: both calls run on the host's main thread and use only `op_shell_save_state`, `op_shell_load_state` and the atomic parameter stores. The shell does not call `op_shell_reset` from them; reset stays on the render thread (Audio Unit reset). A block that starts during a state call is replaced by the dry input, as the ABI says (see Threading).

## Audio Unit events, buses and kind (ABI 2)

The Audio Unit shell renders through `op_shell_process_events`. One source (`native/au/OpenPluginAU.cpp`) builds three component types, chosen when it is compiled; everything below is for all three unless it says otherwise.

| Component | SDK base | Plugin | Note |
|---|---|---|---|
| `aufx` effect | `AUEffectBase` | `OP_KIND_EFFECT` | no MIDI |
| `aumu` instrument | `MusicDeviceBase` | `OP_KIND_INSTRUMENT` | no main input; MIDI in |
| `aumf` music effect | `AUMIDIEffectBase` | `OP_KIND_EFFECT` or `OP_KIND_NOTE_EFFECT` | MIDI in |

- **Type.** `-DOP_AU_TYPE=auto` (the default) builds and runs `native/au/kind_probe.c` against `OP_RUST_LIB` at configure time and takes `aumu` for an instrument, `aumf` for a note effect and `aufx` for every other plugin. An effect is `aufx` even though the default `note_ports()` has a MIDI input, so a plugin that wants to be a music effect says `-DOP_AU_TYPE=aumf`. The type goes into the Info.plist (`@OP_AU_TYPE@`) and into the shell (`OP_AU_TYPE_CODE`). `OP_AU_SUBTYPE` and `OP_AU_MANUFACTURER` are unchanged. `Initialize` fails with `kAudioUnitErr_FailedInitialization` if the compiled type does not fit `op_shell_kind()` (an instrument built as `aufx`, an effect as `aumu`).
- **MIDI in.** `MusicDeviceMIDIEvent` reaches `HandleMIDIEvent` with its sample offset into the next render. A note on with velocity above 0 is `OP_EVENT_NOTE_ON`; a note off, or a note on with velocity 0, is `OP_EVENT_NOTE_OFF`; anything else is `OP_EVENT_MIDI` with the three bytes. Events wait in a 1024 event queue (a spin lock held for one copy, no allocation) and the render drains it. SysEx and MIDI 2.0 event lists are not passed on.
- **Parameter events.** `AudioUnitSetParameter` with a buffer offset above 0 and the immediate events of `AudioUnitScheduleParameters` become `OP_EVENT_PARAM_PLAIN` at that offset; the parameter ends the render at its last event's value, so `AudioUnitGetParameter` sees it. A value with no offset is stored and reaches the plugin at the start of the next render, as before. A ramp is cut into steps 16 frames apart (a step is an event) that end on the end value, so the plugin hears a staircase within one step of the line, not a slope. Events and ramp steps share the 1024 event queue; the excess is dropped (the call that fills it fails). A render longer than the 65536 frames the engine is made for is split, and the events follow their piece.
- **MIDI out.** When `op_shell_note_ports()` has `OP_NOTE_PORT_OUTPUT`, `kAudioUnitProperty_MIDIOutputCallbackInfo` returns one stream named "MIDI Out" and `kAudioUnitProperty_MIDIOutputCallback` takes the host's callback. After each piece the shell reads `op_shell_midi_out` and calls the callback with a `MIDIPacketList` whose time stamps are sample offsets from the render's time stamp, as the property says. The packet buffer is made at `Initialize`; a full list is sent and restarted.
- **Transport.** `HostCallbackInfo` is read once per render: `transportStateProc2` (or `transportStateProc`) gives playing, recording (the second only) and the sample position; `beatAndTempoProc` gives the beat (taken as quarter notes) and the tempo; `musicalTimeLocationProc` gives the signature and the measure's downbeat. The fields the host answered set the flags of `OpTransport` (`HAS_TEMPO`, `HAS_SIGNATURE`, `HAS_BEATS`, `HAS_SECONDS`). Audio Unit gives the downbeat but not the bar number, so `bar_number` is the downbeat divided by the bar length at the reported signature, counted from beat 0; a project that changes signature has its own numbering. With no callbacks only the render time stamp is passed (position and seconds). Later pieces of a split render advance the position and, while playing, the beat.
- **Sidechain.** A plugin with a layout that has a sidechain lets the host set the input element count (`kAudioUnitProperty_ElementCount`, scope input): element 1 of an effect, element 0 of an instrument, is the sidechain. It is used when it is connected and its format fits a layout; otherwise the unit selects a layout without one (or the first layout that fits, with the sidechain silent).
- **Layouts.** `SupportedNumChannels` lists the (input, output) channel counts of the plugin's layouts, plus mono, which has always worked: a plugin with only a stereo layout runs on one channel in and out. `kAudioUnitProperty_SupportedChannelLayoutTags` lists, for the element's channel count, the tags (`native/au/au_layout.h`) whose speaker roles are the plugin bus's, then `UseChannelDescriptions`; mono offers the mono tag and a bus without roles (discrete, ambisonic) `DiscreteInOrder`. `kAudioUnitProperty_AudioChannelLayout` reads back what the host set, or the first tag. The SDK would accept any layout once `UseChannelDescriptions` is listed, so the shell checks it itself: a tag not in the list, or labels the plugin's bus lacks, are refused with `kAudioUnitErr_InvalidPropertyValue`. At `Initialize` the first layout whose channel counts and roles fit the stream formats and the layouts the host set is selected (`op_shell_set_layout`); if none fits, `kAudioUnitErr_FormatNotSupported`.
- **Channel order.** Audio reaches the engine as pointer arrays in the SDK's order (`OpBus::roles`), reordered at the edge: the table gives each host channel's role and the shell points canonical channel `i` at the host channel with that role. No sample is copied. Tags in the table (host order; `Ls`/`Rs` are the back of a 5.1 and the side of a 7.1, by the bus's roles):

  | Tag | Order |
  |---|---|
  | Stereo | L R |
  | MPEG_3_0_A | L R C |
  | Quadraphonic | L R Ls Rs |
  | MPEG_5_0_A, MPEG_5_0_B | L R C Ls Rs; L R Ls Rs C |
  | MPEG_5_1_A (AudioUnit_5_1), _B, _C, _D | L R C LFE Ls Rs; L R Ls Rs C LFE; L C R Ls Rs LFE; C L R Ls Rs LFE |
  | MPEG_6_1_A | L R C LFE Ls Rs Cs |
  | MPEG_7_1_C (AudioUnit_7_1) | L R C LFE Ls Rs Rls Rrs |
  | Atmos_5_1_4 | L R C LFE Ls Rs Vhl Vhr Ltr Rtr |
  | Atmos_7_1_4 | L R C LFE Ls Rs Rls Rrs Vhl Vhr Ltr Rtr |
  | Logic_Atmos_7_1_4_B | L R Rls Rrs Ls Rs C LFE Vhl Vhr Ltr Rtr |
  | Atmos_5_1_2 | L R C LFE Ls Rs Ltm Rtm |
  | Atmos_7_1_2 | L R C LFE Ls Rs Rls Rrs Ltm Rtm |
  | Atmos_9_1_6 | L R C LFE Ls Rs Rls Rrs Lw Rw Vhl Vhr Ltm Rtm Ltr Rtr |

  The top middle pair (`Ltm`, `Rtm`) is the SDK's top side TSL, TSR and the wides (`Lw`, `Rw`) are FLW, FRW. CoreAudio has no other tag with these speakers on the SDK's beds (the Logic Atmos 5.1.2, 5.1.4 and 7.1.2 tags are the same values; CICP 16 has top front and top side pairs, not a bed of the SDK). Channel descriptions map by label (Left, Right, Center, LFEScreen, LeftSurround, RightSurround, LeftCenter, RightCenter, CenterSurround, the surround-direct, top and rear labels, LeftTopMiddle and LeftTopSurround as TSL, RightTopMiddle and RightTopSurround as TSR, LeftWide and RightWide as FLW and FRW). Only buses with more than two channels list `UseChannelDescriptions` (the auval fix: a stereo bus offers `Stereo` only).
- **Layout selection.** `Initialize` always selects the chosen layout on the new engine with `op_shell_set_layout`, layout 0 included. Before, it skipped the call when the engine already reported the layout, but a new engine reports layout 0 without having been prepared for it, so a plugin whose first layout is not its own default (for example one that lists mono first, or a surround layout first) ran with the wrong layout. The one-channel engine of a plugin without a mono layout is not selected, as before.
- **Offline.** `kAudioUnitProperty_OfflineRender` (read and write, global) is stored and sent with `op_shell_set_offline`, also at `Initialize`.
- **Bypass.** As before (see Audio Unit bypass), for any channel count. An instrument has no input to bypass.

Proof: `au_events_proof` over five test components built from one stand-in plugin that implements all of ABI 2 (`native/au/probe_shell.cpp`; what it keeps is `probe.h`): an effect, an instrument, a music effect, and two effects whose library reports ABI 3 and ABI 1.

## Audio Unit parameter text (ABI 3)

The Audio Unit shell shows the plugin's own parameter text, as the VST3 shell does, through `op_shell_param_format` and `op_shell_param_parse`. Main thread only; the render path calls neither and allocates nothing for it.

- `GetParameterInfo` sets `kAudioUnitParameterFlag_ValuesHaveStrings` (also named `HasName`) on every parameter, so a host asks the plugin for text instead of printing the number. `HasCFNameString` was already set. The unit mapping is unchanged: dB, Hz, ms, %, ratio, boolean for a two-step toggle, generic otherwise.
- `kAudioUnitProperty_ParameterStringFromValue` returns `op_shell_param_format` of `inValue` (the current value when `inValue` is NULL) as a CFString; the host releases it. A parameter id out of range or a non-finite value is refused.
- `kAudioUnitProperty_ParameterValueFromString` returns `op_shell_param_parse` of the string as the plain value (the plugin clamps to the range); text the plugin refuses, or an unknown id, gives an error and no value.
- A choice parameter is detected from the ABI: discrete, no unit, 3 to 256 whole steps from `min` to `max = min + steps - 1`, and labels (the format at each step) that are not all numbers. The ABI has no choice flag, so a stepped number such as `0..4` stays a generic parameter. A choice is marked `kAudioUnitParameterUnit_Indexed` and `kAudioUnitProperty_ParameterValueStrings` lists the labels in step order (read once when the unit is made). A toggle keeps the boolean unit and reads `Off` and `On` through ParameterStringFromValue.
- Library below ABI 3: the unit has no parameters (see Versioning), so none of this is reachable.

## Audio Unit bypass

The Audio Unit shell owns `kAudioUnitProperty_BypassEffect`. `AUEffectBase` would copy the input to the output with no delay and reset the plugin when bypass ends, so the shell turns that off (`ShouldBypassEffect` is false, and the property is handled in `SetProperty`). The plugin keeps running while bypassed, so leaving bypass finds it warm. The shell mixes two signals:

- the dry signal, the input delayed by `op_shell_latency` samples, the same value the unit reports as `kAudioUnitProperty_Latency`;
- the plugin output.

A switch moves the mix linearly over 10 ms. Settled bypass is the delayed input exactly. The delay line and the scratch buffers are allocated in `Initialize`, so rendering allocates nothing. A reset (`AudioUnitReset`) clears the delay line on the render thread, with the engine reset described above. The cost is that a bypassed unit still pays for its plugin's CPU.

## Tail

`export_shell!` always exports `op_shell_tail_seconds(instance)`: seconds of ring-out after the input stops, infinity for an endless tail. The value is `Plugin::tail` as of the last processed block. `tail` is called once per block on the audio thread, so it must be cheap and must not allocate. `Tail::Unknown` reports zero. The call works from any thread and never blocks. With `-DOP_TAIL=ON`, VST3 reports it from `getTailSamples`. The Audio Unit reports it as its tail time, with an endless tail given as ten minutes. Without the option VST3 reports no tail and the Audio Unit does not support the property. The SDK example has a finite zero tail, so `-DOP_TAIL=ON` exercises both adapters without a ringing sound.

## Trace

For a host that goes silent and says nothing. Create `<name>-trace.on` in the temporary folder before the first instance is created. `<name>` is the plugin name in lower case, with dashes for spaces and punctuation. The shell then counts creates, destroys, resets, blocks, failed blocks and peaks. The editor's main-thread value updates append a line to `<name>-trace.log` at most four times a second, with the first eight parameter values the engine holds. Without the file, `process` reads one atomic and nothing else. `openplugin_ffi::shell::trace::write` adds a line from plugin code.

## Build

To build a plugin's bundles in every format, with optional signing and notarisation, use `scripts/build_plugin.sh` ([BUILD.md](BUILD.md)). The commands below are what it runs for the shells, and what the proofs use.

The SDK checkouts stay outside this repository. The proofs build `examples/editor`, the `EditorGain` example. Its two parameters are `Gain` (dB) and `Warm` (toggle), and every expected value in the proofs comes from `op_shell_info`, `op_shell_param`, `op_shell_latency` and `op_shell_tail_seconds`, not from constants in the proof.

CARGO_BUILD_JOBS=2 cargo build --release --lib -p example-editor

In this workspace `build-shell` is on the external build volume, not inside the repository, because the internal disk is full.

## Known limits

- Without `OP_EDITOR` there is no editor view: hosts use a generic parameter list, and the AAX view is an empty rectangle. The editor ABI is macOS (`NSView`) only.
- The AAX shell has a page table only with `-DOP_AAX_PAGES=ON`: the build runs `OpenPluginAAXPages`, which writes `<Product>Pages.xml` into the bundle with the parameters in declared order. It needs manufacturer, product and plug-in IDs of four printable characters, so the plugin must set them; the hashed development IDs are refused. Without the option AAX Validator's `test.page_table.load` fails with "Failed to load page tables library".
- AAX has no tail report. This is a format limit, not a gap in the shell. The AAX SDK 2.8.1 (`Interfaces/AAX_Properties.h`, `AAX_Enums.h`, `AAX_IController.h`, `AAX_IEffectParameters.h`, `AAX_IHostProcessor.h` and the `Documentation/Doxygen/dox` guides) has no call, property or notification by which a plug-in states a tail length or a ring-out time; the only latency-like report is `SetSignalLatency`. The one related switch, `AAX_eProperty_Constraint_AlwaysProcess`, stops the host disabling the plug-in's processing when the chain goes silent. It is per effect, costs the whole chain's performance (the SDK says to avoid it unless the host interferes), and carries no duration, so the shell does not set it. `op_shell_tail_seconds` is therefore not used by the AAX shell. The tail contract is checked for VST3 and the Audio Unit only.
- AAX state is one shell chunk (id `OpSt`; layout in `native/aax/OpenPluginAAXState.h`). The shell writes payload version 2: every parameter value, the master bypass, and the blob from `op_shell_save_state` (the parameters plus the plugin's own chunk), so `Plugin::save_state` reaches Pro Tools sessions. `GetChunkSize` asks for the blob size and adds the AAX header; `GetChunk` saves through the size-query protocol (allocate, save, repeat while the state grew) and refuses to write more than `GetChunkSize` promised. The shell reads versions 1 and 2. A version 1 chunk (what 0.3 wrote) restores parameters and bypass and leaves the plugin's own state alone. A load validates the whole chunk first (wrong length, magic, version, parameter layout, blob length, a non-finite or out-of-range value), then applies the blob through `op_shell_load_state`, then the parameters and bypass; a chunk the plugin refuses changes nothing. `CompareActiveChunk` also compares the plugin's blob for version 2. The chunk replaces the SDK's default chunk. `aax_state_proof` drives the real chunk calls on the example, `aax_state_blob_proof` on a stand-in plugin with its own chunk; both build parameter objects without an AAX controller, and Pro Tools itself does not take part. A plugin's state that changes between `GetChunkSize` and `GetChunk` by growing makes `GetChunk` fail rather than overrun the host's buffer; the host asks again.
- The AAX process callback allocates nothing, with or without bypass; `aax_alloc_proof` (the example) and `aax_alloc_latency_proof` (the 200-parameter, 37-sample stub) check it. The proofs cover the callback and the engine it calls, not `EffectInit` or `ResetFieldData`. The delay line, dry buffers and crossfade state are allocated in `ProcessState::prepare`, which `EffectInit` calls.
- The AAX proofs (`aax_text_proof`, `aax_text_stub_proof`, `aax_process_proof`, `aax_state_proof`, `aax_alloc_proof`, `aax_bypass_proof`, `aax_params_proof`, `aax_state_blob_proof`, `aax_alloc_latency_proof`, `aax_events_proof`, `aax_describe_proof`, `aax_roles_proof`, `aax_bundle_proof`) cannot run in CI. They link the Avid AAX SDK, which is not redistributable, so they run only on a machine that has the SDK checked out (`-DOP_AAX_SDK`).
- Avid's AAX Validator runs locally against the example bundle with `scripts/aax_validate.sh`; see `docs/AAX_VALIDATOR.md`. It cannot run in CI either.
- AAX host latency is published by `AAX_CEffectParameters::EffectInit` through `SetSignalLatency`, which needs an AAX host controller. `aax_process_proof` checks that the process engine's `op_shell_latency` matches the ABI; it does not instantiate the AAX controller.
- The AAX parameter manager built by `EffectInit` is assembled from the same `op_shell_param` table, but `EffectInit` needs an AAX controller. `aax_state_proof` builds the same parameters through the controller-free part of `EffectInit` (`proofInit`); the direct process proof checks the packet count, the per-parameter IDs and every default value.
- VST3 state (`getState`/`setState`, `native/vst3/OpenPluginVST3.cpp`) keeps the version 1 head and adds the plugin's whole state as a trailer after the bypass flag. Layout, little-endian: `int32` version 1, `int32` parameter count, one `double` normalised value per parameter, `int32` bypass flag, then optionally `uint32` tag `OPSB` (0x4F505342), `int32` trailer version 1, `uint32` length, and the `op_shell_save_state` blob. The head did not change, so a shell that predates the trailer reads the parameters and ignores the rest, and a state without a trailer (version 1, with or without the bypass flag) loads exactly as before and leaves the plugin's chunk alone. The parameter values come from the head, the blob supplies the chunk; after a load the shell pushes the head's values into the engine, so the two agree. A trailer with another tag or version, a length of 0 or above 1 GiB, fewer bytes than its length, bytes after it, or a blob that `op_shell_load_state` refuses makes `setState` return `kResultFalse` before any parameter, the bypass flag or the plugin changes. `getState` asks the size, copies, and repeats while the ABI answers `OP_STATE_TOO_SMALL` (up to 64 tries); a failed save fails `getState` and writes nothing. With the engine active the blob is the engine's; without one `setState` checks the blob on a scratch instance (created with the prepared rate and block size, or 48 kHz and 512) and keeps it for the next `setActive(true)`, and `setActive(false)` saves the engine's state so a later `getState` still carries it. Both calls run on the main thread and allocate; `process` is untouched and the allocation proofs pass. The controller's `setComponentState` reads only the head, so the controller's parameters match without the blob. A shell that predates the trailer loads such a state's parameters and drops the chunk, without an error. Not claimed: that any host stores the larger state intact, or any DAW session.
- Every shell implements host bypass itself. VST3 exposes the standard bypass parameter (`kIsBypass`, id `0x42595053`, outside the plugin's `0..n-1`); while bypassed it outputs the input delayed by `op_shell_latency` with a 10 ms crossfade on switching, starting at the sample offset of the change, and the engine keeps running so switching back is click-free. The delay line is allocated in `setActive`. The bypass flag is stored as a trailing `int32` after the parameter values in the component state; a state without it (written before bypass existed) loads as not bypassed, and an older shell ignores the trailing flag. The Audio Unit shell handles `kAudioUnitProperty_BypassEffect` itself (see Audio Unit bypass). AAX master bypass also outputs the input delayed by `op_shell_latency` with a 10 ms crossfade; its delay line is allocated in `ProcessState::prepare`.
- `vst3_proof`, `vst3_noalloc_proof`, `vst3_bypass_latency_proof`, `vst3_state_proof`, `au_proof`, `au_bypass_proof`, `au_state_proof`, `au_alloc_proof`, `aax_process_proof`, `aax_state_proof`, `aax_alloc_proof`, `aax_bypass_proof`, `aax_params_proof`, `aax_alloc_latency_proof`, `aax_events_proof`, `aax_describe_proof`, `aax_bundle_proof` and `au_editor_proof` are in-process tests. They load the built bundles in the test process, or call the process callback, and compare the adapter with the C ABI. None of them is a Cubase, Logic, Pro Tools or format-validator session.
- `AUEditorProof` (built with `OP_EDITOR`, ctest `au_editor_proof`) registers the Audio Unit bundle in process, without installing it, and opens the editor as a host does: it reads `kAudioUnitProperty_CocoaUI`, instantiates the factory class from the bundle, makes the view with `uiViewForAudioUnit:withSize:` in an offscreen window and checks its size and that the editor is attached. It uninitializes and initializes the unit with the view open, then clicks a point (default: the centre of the Warm toggle of `examples/editor`; `OP_EDITOR_PROOF_CLICK` `x;y;param` overrides it, shared with the VST3 proof). An `AUEventListener` must see a begin gesture, a value change and an end gesture for that parameter, and the unit's value must change to the value the listener saw. It then closes the view, opens a second one, and disposes the unit first. The window is never shown, but AppKit is initialized, so the proof expects a macOS session with a window server; it has not been run headless and is not in CI. It then sets the view's frame as a host does: a huge and a tiny frame give the editor's largest and smallest size (the range is read back from the view), a frame at the largest size resizes the editor's view, a click at the old position of the Warm toggle hits nothing and a click at the scaled position edits the parameter. A double-click on the bare plate changes the container's frame (what an Audio Unit host observes to size its window). It does not check the re-bind beyond the click still working afterwards, and it does not cover a real host's container (another window, a host that does not follow the frame).
- `VST3EditorProof` (built with `OP_EDITOR`) loads the VST3 in process and opens the editor. It re-creates the engine with the editor open. If `OP_EDITOR_PROOF_CLICK` is `x;y;param`, it checks the edits a click makes. It also resizes the view as a host does: `canResize`, `checkSizeConstraint` (the largest and smallest size, and a size off the 3:2 shape brought to it), `onSize`, `getSize`, the `NSView` frame, a click at the old position (nothing) and at the scaled position of the Warm toggle (an edit). A tiny `onSize` stays at the smallest size. A double-click on the bare plate reaches `IPlugFrame::resizeView`, and the view takes the size the frame grants and keeps its size when the frame refuses.
- VST3 parameter changes, bypass included, are sample-accurate. `process` collects every point of every input queue, orders them by sample offset (ties keep arrival order, parameters before notes), and passes the parameter points to `op_shell_process_events` as events at their offsets; the engine cuts the block and applies each value from its sample. Bypass points cut the block in the shell, and the crossfade starts at the sample of its change. A chunk is also capped at the prepared block size and at `OP_MAX_EVENTS` events, and a block larger than that still works. The scratch for the points is allocated in `setActive` (4096 points, or the parameter count plus one if that is larger, plus room for 1024 note events). A block with more points than that is thinned per queue: each queue keeps an even share of the capacity, keeping evenly spaced points and always its last one, so the last value of every parameter and of bypass is never lost and a long ramp is approximated by fewer steps; a queue beyond the capacity is ignored. A host sends one queue per parameter, so this limit is reached only by more than about 4000 points per block. Points inside one queue at the same offset are merged by the host SDK, not by the shell. The accuracy is that of the plugin: a plugin that smooths a parameter still smooths it from the sample where the new value starts. Starting processing (`setProcessing(true)`) resets the bypass crossfade to the current bypass state. The no-allocation proof is macOS-only (it relies on `malloc_logger`) and covers `process`, not `setupProcessing` or `setActive`, which allocate.
- The AAX controls packet is posted by the shell itself (`GenerateCoefficients` calls `PostPacket`), not by `AAX_CPacketDispatcher`, because a dispatcher packet has a compile-time size. `aax_params_proof` checks what would be posted (`proofTakePacket`); the `PostPacket` call and the data port size declared in Describe need an AAX host, so a 200-value port in Pro Tools is not shown. The AAX SDK sets no limit on the number of parameters or on a native data port's size; the one hard limit found is that a parameter id must be shorter than 32 characters (`kAAX_ParameterIdentifierMaxSize` in `Interfaces/AAX.h`), which the shell does not yet enforce (ids up to 63 characters pass the ABI). `OP_SHELL_AAX_MAX_PARAMS` (64) in `op_shell.h` and `AAX_MAX_PARAMS` in the Rust crate are no longer used by the AAX shell.
- The AAX binary links the external Avid SDK. That binary is not an MIT-only artifact. The SDK license is copied into the bundle resources. Nothing in the build signs it or installs it.

### Resizing in the shells

With `-DOP_EDITOR=ON` the shells define `OP_EDITOR_RESIZE` and follow the editor's size range.

- VST3: `canResize` is false only for a fixed range. `checkSizeConstraint` goes through `op_editor_adjust_size` once the editor is open (before that it clamps to the range alone, without the aspect). `onSize` calls `op_editor_resize`, `getSize` reports `op_editor_get_size`. An editor's request goes to `IPlugFrame::resizeView`; when the frame agrees the view takes the size even if the host does not call `onSize`.
- Audio Unit: the container view overrides `setFrameSize:`. The editor takes the nearest size it accepts and the container keeps the frame the host gave it. An editor's request sets the container's frame size, which a host that observes the view's frame turns into a window size.
- AAX: `GetViewSize` reports the editor's current size. The AAX host never resizes the view by itself, so the only change comes from the editor: its request goes to `AAX_IViewContainer::SetViewSize`, and the editor resizes when the host accepts. No AAX proof covers this, because the view container exists only in Pro Tools; the code is compiled and linked in the `OP_EDITOR=ON` build, and the AAX bundle proofs still pass. An accepted `SetViewSize` and a host that re-reads `GetViewSize` are untested.
